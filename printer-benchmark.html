PheedLoop print hub · spike bench record

Print Path Benchmark

Four printers driven through one Windows print path, measured on the same rig with the same PDF. What each driver reports, what it actually does, and where the two disagree.

PHEEDLOOP-LABS · Windows 11 Pro 26200 PDFium via pypdfium2 updated 2026-09-10 living document, printers added as they land

One pattern organises every result here. Everything about getting bytes onto media generalises. Nothing about knowing what happened does. Scale, colour and vendor settings behaved the same way once pinned, on all three printers tested end to end. Fault reporting, attribution and recovery differed so completely between two printers from the same vendor that no shared promise survives.

01Can the hub drive it unattended?

The question that decides whether a printer needs the Windows agent or a direct vendor SDK.

Zebra ZC10L

HUB-CARD · USB001 · 300 dpi

Viable

Names four faults through the API, recovers automatically, no dialogs. The best-behaved driver tested, and the one with no SDK alternative.

Brother QL-800

USB003 · 300 dpi

Not unattended

A modal dialog sits in the print path and holds the only working Resume. No programmatic recovery found. A stuck job blocks the queue.

EPSON CW-C4000u

(Copy 1) · USB002 · 600 dpi

Prints, faults untested

Cleanest geometry of the four and the only honest colour device. Auto-cut proven to replay both ways. Fault behaviour not yet induced.

Zebra ZD621

ZPL driver · USB004 · 203 dpi

Installed only

Enumerates with 13482 private bytes. No media configured, nothing printed. Also speaks ZPL, so a raw path may bypass all of this.

06What generalises, and what was Zebra all along

Six claims went into this bake-off resting on one driver. Three survived intact.

Generalises · all drivers

Every driver has a vendor-private region, and no portable API reaches it

320 bytes on the Brother, 5836 on the ZC10L, 13482 on the ZD621, 30320 on the Epson. Nobody reports zero. Capture-and-replay is product work, not a tax that one uncertified driver imposes. Public dmScale is inert on every driver tested, the ZC10L included, which is why its zoom trap is reachable only through the private bytes.

Generalises · two vendors proven

A per-job blob handed to CreateDC beats the queue default

Proven on the Epson by a controlled pair. Same PDF, same queue, queue default left at auto-cut on, and the only variable was the pinned blob: the pre-cut capture did not cut, the auto-cut capture did. That is the cleanest experiment in the spike, and it generalises a claim previously measured only on the ZC10L.

Generalises · both directions

A driver's self-description is evidence, not truth

The ZC10L overstates resolution, reporting 315 dpi while printing at 300, and a card came out 5% oversized. The Brother understates colour, reporting DC_COLORDEVICE 0 while printing red. The same defect pointing opposite ways. Never gate behaviour on a capability claim, because only media settles anything.

Zebra-specific · did not generalise

The ten-second queue-default revert

The ZC10L re-asserts its own stored configuration and discards a SetPrinter write within about ten seconds. Brother and Epson both held the same write for 25 s with no drift. Per-job pinning is still correct, because it is the only approach that works everywhere, but the stated reason was wrong.

Zebra-specific · did not generalise

Faults that name themselves, and recover on their own

The ZC10L distinguishes out-of-cards, ribbon-out, jam and cover-open as four codes within a second, and reprints itself once the fault clears. The Brother reports a single generic ERROR in which media-out and cover-open are byte-identical, needs a human to click a dialog, and blocks every job behind the stuck one. So "the iPad can name the actual problem to a desk" is a Zebra promise, not a Windows one.

Zebra-specific · and it was the only one

The single pre-flight signal that ever existed

Cover-open on the ZC10L was the one fault visible on an idle queue anywhere in this spike. On the Brother nothing is visible while idle: a jam with the error light lit reports Normal. No printer here can be truthfully described as "ready", and no printer here can confirm that a badge physically exists.

07Adding the next printer

The reproducible sequence. Roughly twenty minutes and one or two pieces of media.

  1. Install the driver and name the queue

    Installers live in Drivers\, gitignored at about 400 MB. Check the queue is type Local, which a LocalSystem service needs.

  2. Configure the media by hand in the vendor UI

    Unavoidable, and the reason spike 2 exists. Click through to Apply even if nothing looks changed: the Epson's private geometry stayed stale at the previous form's size until a second trip through its dialog.

  3. Read the objective fields 
    benchmark.py "<queue>"

    Gives resolution, private-region size, the imageable area, whether full bleed is possible, and author_mm, the page size whose PDFium raster lands exactly on the imageable pixel count.

  4. Capture a restore point before touching anything 
    devmode.py capture "<queue>" devmode\<name>.devmode
  5. Build a calibration card at that exact size 
    make-test-card.py <author_w> <author_h> <h-target> <v-target>

    Targets shrink to fit and the layout zones itself. Prefer the longest axis for the vertical target: the Epson's 250 mm target is two and a half times more sensitive to a proportional error than the ZC10L's 100 mm.

  6. Dry-run before spending media 
    pdfium_print.py "<queue>" <card.pdf> --devmode <blob> --dry-run

    Require clipped=False and a scale error under 0.02 mm. This step also verifies the blob resolves to sane geometry, which is the check that made a stale Epson blob safe to pin.

  7. Print one, and have a human measure it

    Calipers on both targets. No amount of correct-looking JSON substitutes: the rig reported perfect geometry for a printer that was physically unplugged.

  8. Break it on purpose, with the monitor running 
    spike4_monitor.py "<queue>" --interval 0.5

    Test each fault twice, idle and with a job in flight, because most drivers say nothing until a job arrives. Induce media-out, cover-open and a USB pull. Watch for a driver dialog, because that alone disqualifies a printer from unattended use.

  9. Prove a vendor setting replays

    Change one vendor-only setting by hand, capture a second blob, devmode.py diff them, then print with each pinned against the other's queue default. Pick a setting whose failure is visible without instruments: an uncut badge beats a 5% oversized card for showing a team.

08Open

Free, and no media: does SumatraPDF open the Brother, Epson and ZD621 queues? That settles how much of the renderer finding was the ZC10L being an outlier rather than the renderer being weak. One label each for two more: whether Brother magenta and yellow also print red, which decides how a two-colour badge may be authored, and whether deleting a stuck Brother job unblocks the queue, the one recovery route not yet ruled out.

The ZD621 needs media configured and everything from step 3 down. It also speaks ZPL, a published and stable language, so a raw WritePrinter pass-through would bypass GDI, DEVMODE and the renderer entirely. That is a different architecture rather than a variant of this one, and worth an hour before any driver work.

One hazard on the bench: EPSON CW-C4000u is enumerable by EnumPrinters and absent from the Windows printer list, while (Copy 1) is the working queue. Identical public fields, different private regions. An agent that picks a queue by enumeration can pick one that nobody can see or fix.
