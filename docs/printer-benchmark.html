PheedLoop print hub · spike bench record

Print Path Benchmark

Five printers driven through one Windows print path, measured on the same rig with the same PDF. What each driver reports, what it actually does, and where the two disagree.

PHEEDLOOP-LABS · Windows 11 Pro 26200 PDFium via pypdfium2 updated 2026-09-10 living document, printers added as they land

One pattern organises every result here. Everything about getting bytes onto media generalises. Nothing about knowing what happened does. All five printed correct geometry through one unchanged code path — 203 to 600 dpi, PVC card through continuous tape through die-cut label through folded badge stock, four vendors' driver models, no conditionals anywhere in the renderer. Meanwhile the three whose faults were induced put the answer in three different API fields, and two printers from the same vendor disagreed so completely that no shared promise survives.

01Can the hub drive it unattended?

The question that decides whether a printer needs the Windows agent or a direct vendor SDK.

Zebra ZC10L

HUB-CARD · USB001 · 300 dpi

Viable

Names four faults through the API, recovers automatically, no dialogs. The best-behaved driver tested, and the one with no SDK alternative.

Brother QL-800

USB003 · 300 dpi

Not unattended

A modal dialog sits in the print path and holds the only working Resume. No programmatic recovery found. A stuck job blocks the queue.

EPSON CW-C4000u

(Copy 1) · USB002 · 600 dpi

Prints, faults untested

Cleanest geometry of the four and the only honest colour device. Auto-cut proven to replay both ways. Fault behaviour not yet induced.

Zebra ZD621

ZPL driver · USB004 · 203 dpi

Prints, faults untested

Cut mode proven to replay on a four-byte diff, the tightest in the spike. The only sub-300 dpi device here. Also speaks ZPL, so a raw path may bypass all of this.

DYMO 550 Turbo

USB005 · 300 dpi

Prints, faults untested

Prints on genuine stock and refuses third-party labels by RFID. Reports the best fault text of the five, in pStatus. Worst margins.

06What generalises, and what was Zebra all along

Six claims went into this bake-off resting on one driver. Three survived intact.

Generalises · all drivers

Every driver has a vendor-private region, and no portable API reaches it

320 bytes on the Brother, 5836 on the ZC10L, 13482 on the ZD621, 30320 on the Epson. Nobody reports zero. Capture-and-replay is product work, not a tax that one uncertified driver imposes. Public dmScale is inert on every driver tested, the ZC10L included, which is why its zoom trap is reachable only through the private bytes.

Generalises · three vendors proven

A per-job blob handed to CreateDC beats the queue default

Proven twice by controlled pairs, with the queue default left deliberately hostile and the pinned blob the only variable. The Epson cut or did not cut according to which blob was pinned; so did the ZD621. The ZD621 pair is the tighter proof: its two blobs differ by 4 bytes out of 13702 with the public section byte-identical, so no page geometry is involved and only vendor flags can be carrying the behaviour.

Three vendors now hold a production-relevant setting in bytes no portable API reaches, and a captured blob carries all three: ZC10L zoom, Epson auto-cut, ZD621 cut mode. Two of the three moved exactly four bytes.

Generalises · both roll-fed printers

Roll-fed printers default to not cutting, and cut is never a DEVMODE field

The Epson did not cut until the setting was enabled by hand, and neither did the ZD621. For this class of hardware the default failure mode is a badge still attached to the roll: invisible to every portable API, and carried only by the captured blob. Four bytes out of 13702 separate a badge that cuts from one that does not, while both jobs report scale_pinned: true, identical geometry to 0.002 mm and byte-identical JSON. A hub commissioned with a blob captured too early produces uncut output for ever and reports success throughout.

Generalises · both directions

A driver's self-description is evidence, not truth

The ZC10L overstates resolution, reporting 315 dpi while printing at 300, and a card came out 5% oversized. The Brother understates colour, reporting DC_COLORDEVICE 0 while printing red. The same defect pointing opposite ways. Never gate behaviour on a capability claim, because only media settles anything.

Drives the implementation · three printers, three fields

Each printer puts the truth in a different field, so read all three

There is no single place to look. The ZC10L names its fault in the printer status bitfield while its job status actively lies, reading PRINTING for a jammed printer. The Brother reports a generic ERROR and puts the signal on the job as PAUSED|ERROR. The DYMO reports a generic ERROR, does not pause the job, and writes "Unknown label detected" into pStatus — a plain sentence, and the most useful fault report on the bench.

Two consequences for whoever implements this. A detector keyed on JOB_STATUS_PAUSED misses the DYMO entirely. And pStatus must be read even though it is empty on two of the three printers here, because where it is populated it is the only field that says what actually went wrong.

Per vendor · and it inverts

The specific message goes to a dialog on one vendor and to the API on another

Both the Brother and the DYMO raised a Windows dialog on failure, and they chose opposite channels for the useful text. The Brother's dialog read "Cover open." while its API returned Other (1) with an empty ErrorDescription. The DYMO's dialog said only "error" while its API carried the whole diagnosis.

So neither vendor is better across the board. But for a headless agent the DYMO is the better citizen, because the text is where code can read it rather than on a screen in a session nobody is watching. Worth saying plainly, since the DYMO is also the one printer that refused to print and would otherwise score worst of the five.

Constrains badge design, not the agent

At 203 dpi a hairline breaks into dots and 4 pt text is barely legible

One dot at 203 dpi is 0.125 mm, or 0.355 pt. A 0.1 pt line is 0.28 of a dot, so PDFium hands the driver roughly 28% grey and a thermal head, being strictly 1-bit, thresholds it into a scatter of dots. Working floors for a 203 dpi device are 0.5 pt lines and 5 pt text; one dot is the theoretical floor and looks ragged.

This is the first limit in the spike that belongs to the printer rather than to a driver or the renderer, so no code change addresses it. The consequence lands on badge design: a template that reads correctly on the 600 dpi Epson degrades on a 203 dpi ZD621, so templates need a declared minimum-resolution assumption or per-device variants. Worth telling whoever builds the badge designer before they ship 4 pt disclaimer text.

Likely mechanism, offered as a hypothesis rather than a result: the ZC10L is a retransfer card printer rendering continuous tone, so a 28% grey line comes out thin and grey instead of breaking up. If that holds, the real split is 1-bit devices against contone devices, not high dpi against low. The ZC10L card's hairline rung was never examined closely enough to say.

Zebra-specific · did not generalise

The ten-second queue-default revert

The ZC10L re-asserts its own stored configuration and discards a SetPrinter write within about ten seconds. Brother and Epson both held the same write for 25 s with no drift. Per-job pinning is still correct, because it is the only approach that works everywhere, but the stated reason was wrong.

Zebra-specific · did not generalise

Faults that name themselves, and recover on their own

The ZC10L distinguishes out-of-cards, ribbon-out, jam and cover-open as four codes within a second, and reprints itself once the fault clears. The Brother reports a single generic ERROR in which media-out and cover-open are byte-identical, needs a human to click a dialog, and blocks every job behind the stuck one. So "the iPad can name the actual problem to a desk" is a Zebra promise, not a Windows one.

Zebra-specific · and it was the only one

The single pre-flight signal that ever existed

Cover-open on the ZC10L was the one fault visible on an idle queue anywhere in this spike. On the Brother nothing is visible while idle: a jam with the error light lit reports Normal. No printer here can be truthfully described as "ready", and no printer here can confirm that a badge physically exists.

07Adding the next printer

The reproducible sequence. Roughly twenty minutes and one or two pieces of media.

  1. Install the driver and name the queue

    Installers live in Drivers\, gitignored at about 400 MB. Check the queue is type Local, which a LocalSystem service needs.

  2. Configure the media by hand in the vendor UI

    Unavoidable, and the reason spike 2 exists. On the Epson, click through to Apply a second time: its private geometry stayed stale at the previous form's size until a second trip through the dialog. The ZD621 wrote its private geometry immediately, so this is per-driver insurance rather than a universal step.

  3. Read the objective fields 
    tools/benchmark.py "<queue>"

    Gives resolution, private-region size, the imageable area, whether full bleed is possible, and author_mm, the page size whose PDFium raster lands exactly on the imageable pixel count.

  4. Capture a restore point before touching anything 
    python -m printhub.devmode capture "<queue>" devmode\<name>.devmode
  5. Build a calibration card at that exact size 
    tools/make_test_card.py <author_w> <author_h> <h-target> <v-target>

    Targets shrink to fit and the layout zones itself. Prefer the longest axis for the vertical target: the Epson's 250 mm target is two and a half times more sensitive to a proportional error than the ZC10L's 100 mm.

  6. Dry-run before spending media 
    python -m printhub.render "<queue>" <card.pdf> --devmode <blob> --dry-run

    Require clipped=False and a scale error under 0.02 mm. This step also verifies the blob resolves to sane geometry, which is the check that made a stale Epson blob safe to pin.

  7. Print one, and have a human measure it

    Calipers on both targets. No amount of correct-looking JSON substitutes: the rig reported perfect geometry for a printer that was physically unplugged.

  8. Break it on purpose, with the monitor running 
    tools/spike4_monitor.py "<queue>" --interval 0.5

    Test each fault twice, idle and with a job in flight, because most drivers say nothing until a job arrives. Induce media-out, cover-open and a USB pull. Watch for a driver dialog, because that alone disqualifies a printer from unattended use.

  9. Prove a vendor setting replays

    Change one vendor-only setting by hand, capture a second blob, printhub.devmode diff them, then print with each pinned against the other's queue default. Pick a setting whose failure is visible without instruments: an uncut badge beats a 5% oversized card for showing a team.

08Open

Free, and no media: does SumatraPDF open the Brother, Epson and ZD621 queues? That settles how much of the renderer finding was the ZC10L being an outlier rather than the renderer being weak. One label each for two more: whether Brother magenta and yellow also print red, which decides how a two-colour badge may be authored, and whether deleting a stuck Brother job unblocks the queue, the one recovery route not yet ruled out.

The DYMO enforces genuine media, and that is a purchasing fact. It printed correctly on genuine 30252 stock and refused third-party labels outright by RFID, so consumables are a locked-in recurring cost rather than a sourcing choice. Worth weighing before a DYMO goes into a venue kit. Its settings and fault columns are still open, and unlike the others its usable page is tiny: 25.31 × 81.53 mm after margins, which is why the card generator needed a narrow layout at all.

The ZD621 still needs calipers on its label and its fault behaviour induced. The resolution floor is worth measuring on the other three too, now that the ZD621 has shown there is one: it takes no new media, only a closer look at cards already printed, and it would settle whether the split is 1-bit against contone rather than dpi.

It also speaks ZPL, a published and stable language, so a raw WritePrinter pass-through would bypass GDI, DEVMODE and the renderer entirely. That is a different architecture rather than a variant of this one, and worth an hour before more driver work. The DYMO 550 Turbo is the fourth unit still boxed.

One hazard on the bench: EPSON CW-C4000u is enumerable by EnumPrinters and absent from the Windows printer list, while (Copy 1) is the working queue. Identical public fields, different private regions. An agent that picks a queue by enumeration can pick one that nobody can see or fix.
