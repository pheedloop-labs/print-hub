Windows Print Hub: spike results

Recommendation

Build the agent. Do not buy a bridge.

Both gating spikes passed. A cloud relay in the print path is now an unnecessary risk.

The plan defined this test. If spikes 1 and 2 failed, we rent PrintNode for a season. Both spikes passed. A LocalSystem service printed a correct card after a reboot. No user logged in. Another machine on the LAN sent the job.

Two limits apply. The agent cannot tell the iPad that the printer is ready. Question 4 explains this limit. Questions 5 to 8 are open. This spike does not show that one person can configure a screenless box at a venue.

The eight questions

1
Does a service print with no user logged in? Partial · one driver of two

Yes, for the ZC10L. nssm registered the agent as a LocalSystem service. Machine-scope variables reached the service. The box rebooted. No user logged in. A curl command from a second machine printed a card.

The queues are machine-wide. HUB-CARD is in HKLM. Its PER_USER attribute is clear. No per-user queue exists to hide a fault.

Two limits apply. Windows Automatic Restart Sign-On authenticated the account 18 seconds after boot and then locked the screen. Session 1 existed, but no person logged in. This is also the production condition, because that feature is on by default. Nobody tested the Canon CX-G6400, because that printer is not on the desk.

2
Can a stored settings blob reproduce a hand-configured print? Answered · 0.00 mm

Yes. The limit was 0.5 mm. The result is 0.00 mm on both targets. The blob is also necessary, not optional.

The settings blob for the queue is 6056 bytes. The driver keeps 5836 of those bytes private. The agent copies and replays the private bytes in both directions. One test moved the vendor Zoom setting between 100 and 105. Four private bytes changed with it.

The design changed. A write to the queue default does not hold on this driver. The write reports success, and a read returns the correct value. The driver then restores its own settings after about ten seconds. The agent must pass the blob to CreateDC for each job. The plan's original method was correct.

3
Which renderer ships, and under which licence? Answered · PDFium

PDFium, through the pypdfium2 wheel. PDFium is BSD-3. The binding is Apache-2.0. The GPLv3 dependency is gone.

The licence was not the deciding factor. SumatraPDF 3.6.1 cannot print to this queue at all. It fails with Printer with given name doesn't exist. It fails for every settings string, for every flag, and with no settings.

The same GDI path works, and the same PDF prints from the driver dialog. SumatraPDF also cannot accept a settings blob. Question 2 requires that. Two separate reasons exclude it.

4
Which failures can the agent detect, and which must staff see? Answered

The driver names four faults correctly in about one second. It names them only while a job waits in the queue. The next section gives the list. One fact matters more than the list. An idle queue reports a healthy printer for every physical fault.

5
Can one person configure the box with only a phone? Open · not tested

Nobody tested the bootstrap ladder. One fact helps. The Wi-Fi profile is an All User Profile, so the box had a network before any user logged in. A per-user profile gives no network after a reboot. That failure looks like a service fault, not a network fault.

6
Does wireless-venue support enter v1? Open · needs question 5

Question 5 must come first. This decision remains the largest scope lever in the project.

7
Which mini PC, and does its BIOS restore power? Open

The test box is a mini PC, and it did all the work. Nobody fixed a part number. Nobody checked the BIOS power-restore setting by hand. An unattended box needs that setting.

8
C# or Python, and who owns it? Open · more evidence now

This remains a maintainership decision. The spike adds detail about the work. The print code is small. The difficult code calls DocumentProperties, SetPrinter, CreateDC and StretchDIBits through ctypes. Python must define Win32 structures by hand. C# reaches the same functions with less code.

Question 4 — what the iPad can promise

The team caused four faults on the printer. A monitor read three sources twice each second. Each latency starts when the print request arrives.

The agent detects and names these

  • The hopper is empty PAPER_OUT · WMI NoPaper · 0.7 s
  • The ribbon is out NO_TONER · WMI NoToner · 1.0 s
  • A card is jammed PAPER_JAM · WMI Jammed · 0.9 s
  • The cover is open DOOR_OPEN · WMI DoorOpen · immediate, and visible when idle

Staff must see these

  • The printer is off, or the cable is out the spooler status never changes · only WMI WorkOffline, after 20 s · no cause
  • Any fault while no job waits in the queue a jammed printer with a lit error light reported Normal
  • A card printed wrongly no signal exists
  • A card reached the tray, or did not the job leaves the queue the same way
No pre-flight check exists.

Every consumable fault reported a healthy queue until the agent sent a job. So the agent cannot tell staff that the printer is ready. It can only report that the last card failed, and give the cause.

The word sent is correct.

The agent returned state: sent with correct geometry for a printer with no USB cable. The rule against the word printed is now a measured result.

Corrections to the plan

Each error below cost time. The plan document is still the reference for other engineers.

Media size

The stock is 3.5 in wide and 5.5 in high. The plan states 5.5 × 3.46 in. Author every page at 140 × 88 mm landscape. That size prints correctly. Calipers confirm it.

Renderer

The plan expects SumatraPDF to answer spike 3 in one morning. SumatraPDF cannot print to this printer. The diagnosis took most of the first session. Its error message states the wrong cause, and a false printer name gives the same message.

Rig code

The /printers example reads p[2] from the EnumPrinters result. Level 4 returns dicts in this build, not tuples. The route raised KeyError: 2. Only the Session 0 test called that route.

Correct

Spike 2's method is correct. Save the raw bytes. Pass them back for each print. The other option writes them to the queue default, and that option fails on this hardware.

Changes needed before release

  • Render each PDF in a child process. PDFium runs inside the agent process now. One bad PDF stops the whole service, and the service runs with no operator present.
  • Add authentication. The agent starts automatically and listens on every interface. Any host that reaches port 8080 prints a card. A lab accepts this. A venue network does not.
  • Write the dedupe log to disk. The log is in memory. The process now survives a reboot. A repeated job_id after a restart prints a second card.
  • Pass the settings blob for each job, then verify it. An invalid blob is silent. The driver discards it, substitutes its own settings, and reports success. Read the value back and compare.
  • Poll the printer status, not the job status. A job reports PRINTING while the printer is empty or jammed.

Work needed to close the rest

The four open questions need hardware and a venue. They do not need more Windows research.

Half a day repeats spikes 1 and 2 on the Canon, and that completes question 1. One day tests the bootstrap ladder, and question 6 then follows from the result. Half a day covers the purchase work and a manual BIOS check for question 7. Question 8 needs a conversation, not a spike.

Question 4 also changes the iPad design. Staff cannot get a ready light. The agent reports a failure cause in about one second. Design the interface around that message.
